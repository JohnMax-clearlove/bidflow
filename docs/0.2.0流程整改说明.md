# BidFlow 0.2.0 流程整改与成品双审

本次按合成复现审计、此前成品审阅暴露的流程问题和新增双审需求实施。真实投标资料未写入源码、测试或公开文档。

## 修复的问题

| 原问题 | 处理方式 |
|---|---|
| 同一章节被评分报告采信、却被审核报告判为过期 | 统一审核有效性判断，关联该章全部规则、正文及事实、证据版本 |
| 证明任务可用空结果结束，后续页可能漏查 | 必填分块覆盖；无有效证据须说明原因；引用页限定在本任务范围内 |
| 新一轮通过使旧问题消失 | 保留稳定问题编号，关闭须有独立复核的依据及当前版本定位 |
| 人工确认没有明确来源或版本绑定 | 录入时须明确人工确认声明，改价、改稿或更换成品后重新判断有效性 |
| 人工组卷的外部PDF不在终审链内 | 登记原件和锁定副本，记录哈希、页数及对应规则版本 |
| 新旧报告混用，送签记录可能被后续组卷替换 | 报告批次、输入指纹、文件哈希及历史记录可追溯 |
| 人机并行提交可能覆盖另一方结果 | 乐观版本检查在读取前捕获，冲突明确拒绝并要求重新读取后提交 |
| 派工退出成功但实际无产物 | 校验指定产物的存在、非空、哈希变化和正常结束；成功仍待主Agent验收 |

未使用的候选材料可保留待核提示；实际用于响应和计分的证据须完成相应核查。证书性质、类似业绩适用性、内容是否充分等仍由人和Agent核对原页，程序不会用关键词替代判断。

## 新的使用流程

用户可以直接说：“我组卷好了，请对这份待签章PDF做成品双审。”

1. 锁定这次要核查的成品版本，可为外部PDF或程序组卷。
2. 用户根据人工清单核查，pi依据独立任务包核查；初审不互相提供结论。
3. 主Agent汇总双方发现和分歧。内容或资格阻断项未闭环，不能标为通过；普通失分单独列示。
4. 修改后按新版本复核。内容双审通过后，才进入待签章阶段。
5. 签章后登记签章PDF，关联内容版本，检查内容对比及签章完整性。
6. 由用户逐项确认副本、介质、装订、密封和递交事项。系统记录“递交前检查就绪”，不代替实际递交。

用户可以同时是编制者和人工核查人；Agent审核者必须独立。人工确认标记是流程声明，不是身份认证，Agent不得自行填成用户已确认。

命令与数据协议见[成品双审](成品双审.md)。开发期派工使用[pi执行协作](pi执行协作.md)，固定DeepSeek V4.1 Flash与thinking=max（开发仓库内部流程，BidFlow 使用端不依赖 pi 或任何特定模型）。任务只提供必要规则和片段，逐页文本按文件哈希复用；执行日志留在本地，主Agent优先读取简报及关键证据。

## 旧项目继续使用

原件、正文、历史结果保留。缺少人工声明的旧确认、缺少覆盖记录的旧证据任务，以及没有关闭依据的旧问题，不能直接沿用通过状态，需要按新规则补核。无需因此重写投标正文或重新导入全部原件。

独立章节审核仍保留轮次限制；若历史轮次已用完而仍需补充复核，应由用户决定是否追加审核轮次，不自动无限循环。

本版本的软件合成验证不等于真实项目已完成全部验收。工作流可以防止漏项被静默放过、旧结论被无条件复用，并保留处理依据；不能承诺零废标风险。
