# 成品双审：人工与 Agent 独立核查同一份成品

成品双审解决的是“组卷已经完成，但还缺同一版本、人工与 Agent 各自独立核查”的问题。它适用两类成品：

- 用户人工完成的 PDF，例如外部排版、扫描或公证后的待签章文件；
- 本程序 `bidflow build` 生成的实际分页组卷成品（`--assembly` 直接引用当前成品字节）。

程序只负责版本、覆盖、范围、状态和确定性核算。语义判断由两条 lane 完成：一条是用户本人或用户指定人员的 `human` lane，一条是当前 pi/Agent 的 `agent` lane。程序不会用关键词命中冒充语义审核，也不会替用户确认，更不会输出“保证不废标”“万无一失”。

## 两条 lane 与身份声明

| lane | 谁来做 | 录入要求 |
|---|---|---|
| `agent` | 当前 pi 会话按任务包独立核查 | `submit --lane agent --actor Agent标识` |
| `human` | 用户本人或用户指定人员；结果只在用户明确确认后由主 Agent 录入 | 必须同时使用 `--attest-human`，并提供实际确认人 `--actor` |

- 两条 lane 各自 `prepare`，任务包只含锁定成品位置、规则原文与来源、项目事实和必须核查项，不泄露对方初稿、评分或结论。
- 用户本人可以同时是编制者和人工核查人，因此 `human` 的 actor 允许等于 `writer`；`agent` 的 actor 不得等于 `writer`，也不得等于 `human` 的 actor。
- actor 与 `--attest-human` 是身份声明和流程记录，不是安全身份认证。程序无法识别录入者真实身份，真实责任仍由人和主 Agent 承担。
- 人工结果不能由程序自动生成或自动通过；`submit --lane human` 缺少 `--attest-human` 会直接拒绝。

## 状态流

| 状态 | 含义 |
|---|---|
| `awaiting_lanes` | 至少一条 lane 未提交，或存在漏项 |
| `stale` | 输入、规则、证据、原件或本地副本已变化，旧结论失效 |
| `blocked` | 存在未解决的阻断项，不能通过 |
| `content_review_passed` | 内容双审通过，待签章；签章后必须发起新的 signed 双审 |
| `signed_review_passed` | 签章双审通过；提交前事项仍须人工逐项确认 |
| `submission_check_recorded` | 提交前检查已部分记录，仍有事项 pending |
| `ready_for_submission` | 提交前检查已逐项记录；不代表已经提交，也不保证不废标 |

`status` 和 `finalize` 每次都重新计算实际文件哈希、规则/证据指纹和提交覆盖情况。即使记录里曾经写入过通过状态，只要输入或成品变化，再次查看就会显示 `stale`。

## 快速开始

### 一、外部人工 PDF

```powershell
# 1. 锁定成品并发起内容双审（rules 必须已完整拆解并确认）
bidflow final-review start --project . --stage content --writer 编制者标识 --pdf "D:\成果\待签章投标文件.pdf"

# 2. 两条 lane 各自准备
bidflow final-review prepare --project . FR001 --lane agent
bidflow final-review prepare --project . FR001 --lane human

# 3. Agent 读取 .bidflow/../06_审核检查/成品双审/FR001/agent/B01/context.json，
#    按 result_schema 写 result.json 后提交
bidflow final-review submit --project . FR001 --lane agent --result "06_审核检查/成品双审/FR001/agent/B01/result.json" --actor 核查Agent

# 4. 人工核对 06_审核检查/成品双审/FR001/human/人工核查清单.md，
#    用户明确确认后由主 Agent 录入
bidflow final-review submit --project . FR001 --lane human --result "06_审核检查/成品双审/FR001/human/结果模板.json" --actor 人工复核人 --attest-human

# 5. 复算覆盖并记录结论
bidflow final-review finalize --project . FR001
bidflow final-review status --project . FR001
```

### 二、本程序组卷成品

组卷、分页、`assembly` 和 `visual` 确认完成后：

```powershell
bidflow final-review start --project . --stage content --writer 编制者标识 --assembly
```

`--assembly` 直接绑定当前组卷 PDF 的字节。`build --mode ready` 只改变文件路径（复制到 `07_最终输出`），不会改变字节，因此同一份双审在 `ready` 重复执行时仍然有效。

## 结果 JSON 协议

协议 Schema 可用 `bidflow schemas schemas` 重新导出，对应 `schemas/final_review.schema.json`。

```json
{
  "review_id": "FR001",
  "lane": "agent",
  "actor": "核查Agent",
  "attestation": "",
  "items": [
    {
      "id": "CHK-Q001",
      "status": "pass",
      "reason": "已核对锁定成品第1册第2页证照原页与规则原文，主体名称一致。",
      "refs": [{"volume": "V001", "page": 2}],
      "parent_refs": [],
      "verified_original": true,
      "blocking": false,
      "score": null
    }
  ],
  "summary": "逐项结论见items。"
}
```

规则：

- `status` 只能是 `pass`、`risk`、`uncertain`、`not_applicable`；理由不能为空，`not_applicable` 也必须写明原因。
- `refs` 引用成品册 ID 和该册实际物理页，页码不得超过 `page_count`；规则来源页不在这里填写，任务包单独给出。
- 引用了扫描页、图像页或文字可疑页时，必须打开原页核对并把 `verified_original` 置为 `true`。
- 漏项、未知核查项 ID、重复 ID、超出页范围、空理由、未知状态都会被拒绝；全部核查项都被两条 lane 覆盖后 `finalize` 才可能通过。
- `signed` 阶段的规则核查项必须填写 `parent_refs`，指向已通过的内容版实际页，逐页说明签章版与内容版的对比结果。

### 风险与分数分离

- 资格 `Q`、否决 `F`、必响应 `R` 的 `risk`/`uncertain`，以及证书性质、真实性不明等发现，按阻断项处理；核查人认为某发现必须阻断时，可置 `blocking: true`。
- 商务 `S`、技术 `T`、报价 `P` 的缺件和失分只记录得分影响，不会自动升级为废标。
- 评分字段 `score.kind`：`supported`（客观支持）、`conditional`（有条件支持）、`simulated`（技术模拟）、`unknown`（未确定）。技术评分只能是 `simulated` 或 `unknown`；技术模拟分不会与客观确认分合并。
- 分值必须在 `0` 与规则满分之间；规则配置了 `tiers` 档位时，只能填写已配置档位对应的分值，不能凭空推断。
- 两条 lane 对同一核查项的结论不一致时全部保留在报告中：资格 `Q`、否决 `F`、必响应 `R` 以及签章/内容对比核查项的差异会要求解释或闭环，未闭环前不能通过；商务 `S`、技术 `T`、报价 `P` 的单纯评分差异保留双方条件分，不自动升级为废标。
- `finalize` 的分数汇总按 lane 分开列出支持分、条件分、模拟分和未确定项，摘要与明细来自同一份计算结果。

## 版本与新鲜度

- `start` 把成品复制到 `06_审核检查/成品双审/<ID>/inputs` 并记录来源、相对路径、SHA256、页数和版本；原件只读，人工稿不会被覆盖。
- 双审绑定当时的规则、事实、证据、响应指纹和成品哈希。
- 外部原件仍在原位置但被改动、本地锁定副本被改动、规则或证据更新，都会使旧通过失效，`submit` 拒绝过期结果。
- 外部原件路径不可访问时，状态保持可用并给出明确提示：锁定副本仍是本次真实审阅对象，但程序无法核实递交原件与该副本一致；涉及原件的结论以锁定副本为限，并在结论报告中标清。
- 同一版本纠正误报时，由该 lane 提交新的 revision，旧结论保留在历史中；不提供“一键忽略阻断后通过”的捷径。补证或改稿后必须按新版本重新发起。

## 签章阶段

- `content_review_passed` 只表示内容通过。签章完成后，必须用签章 PDF 发起新快照：

```powershell
bidflow final-review start --project . --stage signed --writer 编制者标识 --parent FR001 --pdf "D:\成果\已签章投标文件.pdf"
```

- `signed` 必须关联已通过的 content 记录；关联缺失、关联记录不是通过状态、或关联记录已失效时都会拒绝。
- 两条 lane 都要确认签章真实性与位置，并逐页对比签章版与内容版（`parent_refs`）。不能默认“只是多了章”。
- 签章阶段通过后状态仅为 `signed_review_passed`。

## 提交前人工检查

装订、副本、介质（如 2 套 U 盘）、密封、递交地点时间和保证金等事项不在内容或签章双审内自动通过，必须由人工逐项确认：

```powershell
bidflow final-review submission --project . FR002 --actor 递交确认人 --attest-human --result "提交前检查.json"
```

`提交前检查.json` 示例：

```json
{
  "review_id": "FR002",
  "actor": "递交确认人",
  "items": [
    {"id": "SUB-01", "status": "confirmed", "reason": "按招标要求胶装两册，已核对"},
    {"id": "SUB-03", "status": "not_applicable", "reason": "本项目招标文件未要求U盘介质"}
  ]
}
```

缺项保持 `pending`，`finalize` 后状态为 `submission_check_recorded`；全部逐项确认后为 `ready_for_submission`。这两个状态都不表示已经提交投标，也不保证不废标。

## 上下文与缓存

- 每个成品的逐页文本和图像页疑点索引按文件哈希缓存一次（`.bidflow/cache/final_review/<hash>/structure.json`），可跨双审复用，不会反复 OCR；本功能默认不启用全量 OCR。
- Agent 任务包只给出必要规则原文、来源、册页索引和缓存路径，不包含整本 PDF 全文或图片 base64。
- 规则较多时按预算分批，`submit` 支持独立批次；`finalize` 检查所有批次是否覆盖全部核查项。单条规则都超出预算时明确拒绝并提示拆分，不会静默截断。
- 人工清单可以整表展示，因为用户查看不受模型上下文限制。

## 与待签章输出的关系

`bidflow build --mode ready` 在原有 assembly/visual 确认之外，新增硬性门槛：当前组卷成品必须已有同一字节的 `content_review_passed` 双审记录。旧的 assembly/visual 确认仍然保留，但不能单独绕过内容双审。没有通过内容双审时，命令会明确列出缺口。

## 明确不承诺

- 不代替人工签章、不接受、不提交投标。
- 不承诺零风险、不废标或“万无一失”。
- 不把模型文字当作人工确认；人工结论必须由用户在对话中明确确认后录入。
- 所有真实资料、执行日志和审核报告保留在本机项目目录，不进入公开 Git。
