# 证据核验、计分与人员配置

BidFlow 把三类信息分开保存：

1. **台账记载**：用于寻找候选项目和人员；
2. **材料实际证明**：记录原件、证明页、能够证明的事实和核验人；
3. **本次招标适用性**：把证明材料或正文章节绑定到具体招标规则，并说明为什么满足或仍缺什么。

因此，检索命中不等于符合，参与项目不等于主持业绩，企业合同也不自动证明某个人承担了指定角色。

## 从规则到证据

完成全部拆标任务并核对后，记录规则确认：

```powershell
bidflow confirm rules --actor 项目负责人 --attest-human --project .
```

然后准备证据任务：

```powershell
bidflow task prepare evidence --project .
```

也可以按文件或规则缩小范围：

```powershell
bidflow task prepare evidence --target DOC文件编号 --project .
bidflow task prepare evidence --target S001 --project .
```

命令会生成一个或多个 `.bidflow/tasks/TASK编号/context.json`。其中只包含当前任务允许使用的规则、事实和资料分块，并附带结果 Schema。Agent 应逐份完成以下工作：

- 对照原页判断材料能证明什么，记录准确页码；
- 将 `verification` 区分为 `candidate`、`verified`、`insufficient` 或 `rejected`；
- 建立规则与证据的响应关系，说明适用性、缺项和规则版本；
- 对识别质量为 `review` 的页面，只有查看原页后才能记录 `visually_verified`；
- 声明 `covered_block_ids` 且与任务 assigned 分块完全一致；空 `evidence` 只在全部块确实无有效材料时使用并写明 `no_evidence_reason`；`pages` 只可引用本任务 source_blocks 提供的物理页，无页映射不得猜测；
- 不从台账或历史正文直接生成“已核验证据”。

Agent 按 Schema 写入 `result.json` 后接收：

```powershell
bidflow task accept --task TASK编号 --result .bidflow/tasks/TASK编号/result.json --actor 材料核验Agent --project .
```

程序会检查任务版本、允许引用的文件、分块覆盖声明、证明页范围、原件哈希、规则版本和执行者。结果过期会被拒绝，不会静默覆盖新资料。每次接收会写入带 `task_id`、块哈希和文件哈希的 `evidence_coverage`；只有带自身当前覆盖的 accepted 任务才会被 `prepare` 复用，旧结果缺少覆盖时会重新生成任务，不会被静默当作已完成。

## 查看匹配和缺件

```powershell
bidflow match --project .
bidflow reports --project .
```

`match` 会逐项检查规则来源、证据版本、证明页、有效期、人员和项目身份、指定角色、正文、表单及人工事项。`reports` 会重建：

- `02_招标拆解/资格审查表.md`；
- `02_招标拆解/否决风险表.md`；
- `02_招标拆解/评分规则表.md`；
- `02_招标拆解/bid_spec.json`，汇总当前项目事实、设置、规则和全量分析覆盖记录；
- `03_资料匹配/资料匹配表.md`；
- `03_资料匹配/商务评分测算.md`；
- `03_资料匹配/待补资料及借阅清单.md`；
- `04_技术标策划/技术评分响应矩阵.md`；
- `04_技术标策划/技术标策划.md`；
- `06_审核检查/技术评分覆盖复核.md`、审核清单和技术模拟评分；
- `06_审核检查/报告清单.json`：记录报告批次、共同输入指纹、审核编号和各文件 SHA256；旧批次归档在 `06_审核检查/报告历史/`，可判断报告是否过期或被人工改动。

借阅清单会保留项目名称、合同编号、台账角色、待证明事项和建议借阅内容。拿到补充材料后导入项目，再准备新的 evidence 任务。

## 计分口径

```powershell
bidflow score --project .
```

程序只按拆标结果中明确记录的确定性计分规则计算。商务部分分成：

- `business_supported_score`：当前有效证据支持的测算分；
- `business_potential_additional_score`：候选证据补齐后可能增加的分。

支持固定分、按有效且去重的证明项计分、封顶、互斥和明确的分配规则。Agent 在响应中自报的分值不能替代程序核验。技术分只展示独立 Reviewer 对当前正文的模拟评分；报价分单独列示，在评标公式和所需报价数据不完整时保持待核。

所有分数都是投标阶段测算，不是评委最终得分。

运行 `bidflow staff --config 人员配置.json --project .` 后，程序还会把最近一次可追溯的组合比较写入 `03_资料匹配/人员配置建议.md`。达到枚举上限时，报告只称为已检查范围内的候选方案，不宣称全局最优。

## 人员方案

先把人员台账和证明材料导入，明确可用性、岗位资格、评分规则和兼岗限制。人员配置文件示例：

```json
{
  "max_combinations": 10000,
  "require_available": false,
  "allow_dual_roles": false,
  "positions": [
    {
      "id": "leader",
      "title": "项目负责人",
      "candidate_ids": ["EMP-001", "EMP-002"],
      "eligibility_rule_ids": ["Q002"],
      "scoring_rule_ids": ["S002"]
    },
    {
      "id": "member",
      "title": "项目成员",
      "candidate_ids": ["EMP-002", "EMP-003"],
      "scoring_rule_ids": ["S003"]
    }
  ],
  "incompatible_staff": [["EMP-001", "EMP-003"]]
}
```

```powershell
bidflow staff --config .\人员配置.json --project .
```

程序先排除已确认不可用、缺台账来源、资格证据不足或不满足明确硬条件的人员，再枚举允许的组合。默认返回当前范围内得分优先、缺件较少的前三套方案。

`available: null` 表示仍需用户确认人员能否参加。达到 `max_combinations` 上限时，结果会标明只检查了部分组合，并且不会声称已经找到全局最优方案。

人员和证据选择核对完成后可记录：

```powershell
bidflow confirm selection --actor 项目负责人 --attest-human --project .
```

人工确认必须由主 Agent 在用户明确确认后以 `--attest-human` 录入；它只是流程声明，不是身份认证，程序不能证明操作者真实身份。此确认只对当前规则、证据、响应、人员、业绩和项目事实版本有效；改报价、改正文或改成品后自动失效，需重新确认。

## 审核底线

以下情形不能记为“已有证据支持”：

- 原始文件缺失、被修改或哈希不一致；
- 证明页缺失、超出页数或低质量页面未经原页核对；
- 证书在投标截止日已过期，或截止日期尚未确认导致有效期无法判断；
- 材料未写明指定人员、项目或角色；
- 台账、方法论或历史优秀章节被当作正式证明；
- 证据文件未完成当前分块覆盖核查，或引用了本任务未提供的页码；
- 复核发现未通过绑定当前正文 sha、实际定位和有效证据的 `resolutions` 关闭；
- 响应仍有缺项、引用旧规则，或规则本身未确认；
- 同一项目或证据违反去重、互斥、最低数量等明确计分条件。
